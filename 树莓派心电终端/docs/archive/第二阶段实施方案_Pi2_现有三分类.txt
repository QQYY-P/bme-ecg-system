树莓派 2 与现有三分类模型的第二阶段实施方案

文档已归入 docs/。下文未特别标注的源码、运行命令及本地目录均以“树莓派心电终端/”为基准；历史验证按原日期保留。
设计日期：2026-10-26

一 方案目标和当前状态

固定使用照片中的 Raspberry Pi 2 Model B V1.1 和已有 N/PVC/PAC 三分类模型。
默认保留 seed42、seed43、seed44 三个 ResNet-1D 的 softmax 概率平均，不重新训练、不擅自删减为单模型。
目标为单导联心电教学原型：STM32 稳定采样，Pi 2 采集、显示、参数计算和本地分类，服务器负责汇聚、历史查询与远程访问。
本文件是设计方案。下述“可实现”指工程可行性判断，所有 Pi 2 上的速度和稳定性尚未验证。

现有可复用内容：STM32 360 Hz 固件、三字节解析器、50 Hz 陷波器、心拍检测和预处理、三模型权重。
此前新增的 NumPy FP32 推理原型已在电脑通过 24 项协议、滤波、预处理和数值参考测试。
尚未完成 Pi 2 安装、完整界面、物理串口联调、HRV、报警、云端和 INT8 端侧运行。
课程硬件方案列 >=4 GB；本方案按用户选择使用 1 GB Pi 2，属于硬件配置偏离，报告中需如实列出，不能声称满足此项。

二 总体结构

AD8232 -> STM32 ADC / TIM3 / DMA -> 115200、8N1 USB-TTL -> Pi 2
Pi 2 收到数据后分为四条路径：
1. 原始路径：原始 ADC、序号、质量标记、会话信息 -> 分块保存 -> 云端补传。
2. 显示与参数路径：有状态滤波 -> QRS/RR/心率 -> 轻量屏幕显示及参数越限提示。
3. 模型路径：原有预处理 -> 三模型集成 -> N/PVC/PAC 预测、概率、采样时刻及结果产生时刻。
4. 网络路径：读取已保存的待上传块 -> HTTPS API -> 服务器数据库 -> 电脑网页/手机端。

Pi 2 安装支持该板的 32 位 Raspberry Pi OS，目标 Python 3.11+。
先使用已有 HDMI 显示器；界面以 800x480 为最小设计基准，可随屏幕伸缩，实际屏幕尚未确认。
本地界面采用 Tkinter Canvas，避免同板同时运行桌面界面、浏览器和完整 Web 服务。
联网优先使用有线以太网；需要无线时再评估兼容 USB 网卡。
人体采集沿用课程对供电和隔离的要求，USB-TTL 本身不提供电气隔离。

三 第二阶段要求逐项对应

1. 模拟前端与树莓派采集平台：保留。
   使用现有 AD8232 + STM32 + USB-TTL，不重复增加 Arduino 或另一块 ADC。
   360 Hz 位于课程 250-500 Hz 范围内；树莓派不承担精准定时采样。

2. 预处理：可实现，分支处理。
   显示支路使用 50 Hz 陷波和低阶有状态带通，提供原始/处理后波形切换。
   基线去除及带通参数固定在配置中，并验证频响、瞬态和分块一致性。
   模型支路必须沿用已有处理，不能把显示支路的新增滤波直接叠加到模型输入。

3. 信号质量检查：先实现基础版本。
   记录导联无效、非法帧、序号异常、ADC 饱和、平直段、接收中断及接收速率。
   可计算工频频带功率占比等指标；无干净参考信号时不把它称作真实 SNR。
   输出“可分析/信号待检查/数据中断”等工程状态，不能据此声称完成临床质量判定。

4. QRS、RR 和心率：可实现，优先完成。
   先以现有 RPeakDetector 联调界面和指标，再补充并验证课程点名的流式 Pan-Tompkins 路径。
   现有 RPeakDetector 是窗式能量检测器，不能直接改名为标准 Pan-Tompkins。
   该路径服务于实时参数；模型内部检测器保持不变。两种峰来源须分别标识。
   HR=60/RR_seconds；同时可显示最近若干有效 RR 的稳健平滑心率。
   缺口、脱落或持续无可信峰时停止更新并显示“无有效数据”，不保留旧值冒充当前心率。

5. SDNN/RMSSD：可以计算，质量控制需补充。
   保留原始 RR 和清洗后的 NN 候选，不跨采样缺口构造相邻间期。
   记录剔除原因、有效比例、分析时长；早搏/伪峰/漏峰未妥善处理时只称 RR 统计预览。
   模型的 PAC 识别较弱，不能仅凭预测 N 就保证是正常窦性间期。
   初版可显示短窗预览，正式对照采用固定 5 分钟记录和可复核的清洗规则。

6. LF/HF：可做，后置且低频更新。
   先收集 5 分钟质量合格的间期序列，再估计频谱；建议每 30-60 秒刷新一次。
   可先在电脑/云端实现复核，板端只展示结果和窗口时间；这属于计算位置简化。
   3 分钟采集演示与 5 分钟 HRV 评估分开安排，不强行把短窗数字当作完整 HRV 结论。

7. 在线心律识别：部分覆盖，吞吐需板测。
   保留 N/PVC/PAC 三分类，逐拍输出预测，不改标签含义。
   不包含房颤类别，也无 OTHER 拒识类；RR 不规则不能直接命名为房颤。
   界面显示“模型预测”，PAC 结果待复核。原历史验证 macro-F1 约 0.540，PAC 精确率约 2.72%、召回率约 30.60%。
   数值迁移通过不代表识别能力提高，课程报告需保留这些限制。

8. 心率异常报警：可实现。
   使用可配置的演示阈值、持续时间和恢复滞回，区分心率越限与设备/信号故障。
   先做屏幕变色、事件记录和确认按钮；声音提示后置。
   不把一次 PVC/PAC 预测直接升级为紧急报警，不把检测不到 R 峰直接判为停搏。

9. 监护仪式界面：可实现，降低显示负担。
   默认 5-10 秒波形，10-15 帧/秒；参数每秒刷新；分类到达时刷新列表。
   显示峰值保留抽稀，不改变原始保存数据或 360 Hz 模型输入。
   主界面保留波形、HR、RR、导联/连接状态、最近分类和录制计时。
   HRV、详细概率、历史记录和网络设置分别放在独立页面。
   可填实验编号、备注；不必为教学演示采集真实姓名等身份信息。

10. 本地存储、历史查询和 3 分钟报告：可实现。
    原始数据连续落盘，界面只留约 30 秒环形缓存；不能沿用旧上位机“仅导出最近 120 秒”作为完整录制。
    SQLite 保存会话、数据块索引、事件、分类和上传状态；原始块用紧凑二进制文件，按需导出 CSV。
    每秒或固定点数提交，磁盘不足或写入失败必须显式提示；不假称数据已保存。
    3 分钟报告列接收点数、有效率、脱落比例、已观察到的序号异常、饱和/平直段、速率变化和滤波前后频谱。

11. 边缘模型运行：先跑通 FP32，再评估实时性。
    采用已经转换的 NumPy + SciPy 原型，减少 ARM32 上对 PyTorch 安装的依赖。
    这仍是原深度网络的推理实现，但不是在 Pi 2 上运行 PyTorch，也不是 INT8 引擎。
    使用独立模型进程和有界队列；模型异常时采集、存储和基本显示继续工作。

12. INT8 与 ONNX/TFLite：必须单列为后续适配任务，不能直接省略后仍称全部达标。
    在电脑完成现有网络导出、代表性数据校准及量化前后逐类评估，不在 Pi 2 上训练。
    优先调查 TFLite/LiteRT ARMv7 armhf 的 C/C++ 运行路径；官方有 ARM32 交叉编译说明，但所列 ARMv7 示例验证设备为 Pi 3/4，Pi 2 仍需编译与运行验证。
    Conv1D 必要时用保持等价的二维运算表达；残差、池化、RR 分支、softmax 和三模型融合均须核对。
    需要覆盖主干卷积的静态量化；只量化全连接层不一定有明显收益。
    量化数据从训练/校准集选取，不使用最终测试集调参；报告 per-class precision/recall/F1、macro-F1 和混淆矩阵。
    只在电脑完成量化文件仍不等同于板端 INT8 运行完成；失败时保留 FP32 原型并将该项标为未完成。

13. 云端汇聚与 Web：可实现，服务放在板外。
    Pi 2 仅做客户端，优先采用 HTTPS 批量上传；第一版不同时引入 MQTT。
    本地持久化待上传队列，断网仍采集；使用 session_id + chunk_id 去重，确认后标记已上传。
    先传会话信息、每秒参数和分类事件；原始波形分块上传，供完整历史查询。
    服务器提供接口、数据库和网页；网页显示最新数据、历史波形和设备状态。
    首先在局域网电脑联调，再部署到实际云服务器；局域网演示本身不称为云端部署。
    云端重算可以复用同一三分类作为一致性复核，但不能被描述为独立临床验证。

14. 移动 App：简化为手机网页起步，App 交付另列。
    先做同一 Web 页面适配手机；如果要求明确安装 App，再做 Android WebView 外壳或独立轻客户端。
    手机网页可访问不等于已经交付 Android/iOS App；报告分别列状态。

15. 外壳：课程为可选项，最后完成。
    优先满足固定板卡、绝缘、走线、散热与接口可达性，不占用首轮联调时间。

四 模型输入及延迟约定

固定 360 Hz、单导联、原极性；模型输入为峰前 90 点和从峰起 90 点，共 180 点。
形态支路逐拍去首尾线性趋势、z-score；RR 仅使用历史间期，不读取未来心拍。
分类前保留当前 50 Hz 陷波设置，连续段前 2 秒预热；每 10 秒核心窗口配上下文。
首次约需 14 秒连续有效数据，加模型加载与计算耗时；之后每 10 秒形成一批结果。
单拍结果具有约 2-12 秒算法确认延迟，再加计算与排队时间，不能称为逐拍即时报警。
异常数据会清空相关状态并重新积累；分类页面显示输入窗口、采样时刻、产生时刻和数据来源。
暂停显示不暂停采集；模型关闭不关闭原始记录；断开串口建立新的会话边界。

五 并发和资源预算

接收线程：串口读取、解析、质量标记、分发。存储线程：按块持久化。
参数线程：流式滤波、QRS、RR、心率。主线程：界面和控制。
分类进程：只接收模型必要样本/时间/连续段标记；模型常驻，避免反复加载。
上传线程：只从持久化队列取任务，网络延迟不能阻塞接收。
所有队列有界；原始记录队列满或写盘失败时标记失败并安全停止录制，不静默丢样。
显示队列可合并为最新快照；分类队列溢出必须记录未分类时间范围、清空上下文，禁止跨缺口拼接。
历史查询和 CSV 大文件导出在停止录制后优先执行，初版避免与采集争用磁盘。
测试 BLAS 1/2 线程配置，避免多个工作线程各自占满所有核；优先保证接收和界面响应。

静态计算结果，不是 Pi 2 实测：
三字节串口：360*3 = 1080 字节/秒有效载荷；8N1 线速约 10800 bit/s，小于 115200。
3 分钟：64800 个点、194400 字节原始帧，不含文件头和时间/质量元数据；CSV 会更大。
三个融合权重数组：每个 2203420 字节，总计约 6.30 MiB；不含运行时、临时矩阵与系统桌面内存。
单模型卷积和全连接约 8612352 MAC/拍；三模型约 25837056 MAC/拍，不含检测、滤波与其他运算。
因此不能由“文件很小”推断实时性；实际瓶颈须按板端整条流水线测量。

六 板端验证与简化顺序

以下是项目建议验收目标，不是已经达到的指标，也不是课程原文数值。
1. 记录板型、OS 位数、Python/NumPy/SciPy 版本、CPU 温度、是否发生降频及供电异常。
2. 先运行已有 36 拍参考和协议测试，再做按原速输入的合成/录制回放；保存概率误差和类别一致率。
3. 同时打开采集、绘图、存储和三模型，记录每 10 秒任务的检测+推理用时、队列长度和结果延迟。
   初步目标为 P95 用时 <=5 秒且长时间无增长积压；最低必要条件是平均处理速度持续跟得上 10 秒新数据。
   用较快心率、多候选峰和噪声数据压力测试，不能只用一段低心率正常样本证明吞吐。
4. 先完成至少 3 分钟连续录制和质量报告，再做 30 分钟稳定性测试。
   记录采集是否中断、观察到的序号异常、无效点、进程峰值内存、剩余内存和是否持续换页。
5. 插拔串口、导联无效、断网恢复、模型文件缺失、磁盘空间不足等场景单独测试。
6. 量化成功后重复板测，并用未参与校准的测试集比较 FP32 与 INT8；功耗用外部电源测量设备记录。

性能不足时的顺序：
A. 保持三模型不变，显示由 15 降到 10 帧/秒，关闭同时展示两条曲线，HRV 降低更新频率。
B. 优化卷积实现、批大小、BLAS 线程、内存复制及上传调度，再测量。
C. 对同一网络进行 ARM32 优化引擎/INT8 适配，重新评估精度和吞吐。
D. 若仍跟不上，保留完整采集、心率和波形，三分类改为明确的停止后分析或指定片段分析；标明未达到全量在线分类。
不通过降低 360 Hz 输入采样率、改变 180 点窗口或无提示漏掉心拍来“提速”。
仅把每 10 秒任务改成每 20 秒处理两份数据，不会解决持续吞吐不足。
若未来决定从三模型变为其中一个模型，属于另一个运行配置，需明确选择并做准确率对照，不在本方案自动执行。

七 串口协议限制

当前为 8 位序号 + ADC 高/低字节，没有帧头和 CRC；0xFFFF 表示导联状态导致无效。
第一版采用打开串口后手动复位 STM32，非法值或失步时停止相关分析并提示重连。
8 位序号无法识别全部丢失、重复、乱序或复位，也不能发现所有恰好仍为合法值的字节错位。
因此质量报告写“观察到的序号异常”，不能仅凭序号宣称绝对零丢包。
完整无人值守自动恢复需要后续同时升级固件和接收端：帧头、长度、较长序号、采样率、状态及 CRC。
网络分块校验只能验证上传过程，不会弥补原 UART 协议已经遗漏的错误。

八 模块划分和实施顺序

已有模块：protocol.py、notch_filter.py、ecg_classifier.py、numpy_predictor.py、models/。
拟新增模块：
  app.py                    主入口与停止/恢复生命周期
  acquisition.py            串口接收与会话分段
  signal_analysis.py        显示滤波、QRS、RR、心率、HRV
  quality.py                基础信号与通信质量统计
  inference_worker.py       独立进程、队列、延迟和结果
  recording.py              分块落盘、索引、CSV 和质量报告
  alarms.py                 越限持续判定、恢复和事件确认
  ui/                       波形、参数、分类、历史和设置页面
  uploader.py               持久化补传、确认和重试
  config.json               串口、屏幕、分析参数和服务地址
  tools/benchmark_pi.py      真实板端速度、队列与内存报告
服务器端另设 API、数据库、Web；不把整套服务安装在 Pi 2。

第一步：Pi 2 环境检查、模型参考回放和耗时测试，优先消除最大不确定性。
第二步：串口 + 基础质量 + 原始落盘 + 轻量波形，产出 3 分钟记录。
第三步：心率/RR + 三分类 + 事件提示，确认两条分析路径互不阻塞。
第四步：HRV、历史查询、质量报告、异常场景与长时间稳定性。
第五步：HTTP 汇聚、Web 与手机网页，联调后实际部署云端。
第六步：同模型 INT8 与板端引擎适配，形成精度/延迟/内存/功耗对照；App 外壳和外观后置。
若第一步发现 FP32 明显跟不上，优先提前第六步的引擎适配，不等全部界面写完再发现核心问题。

九 计划交付与尚未覆盖项

基础交付：Pi 2 程序、可复核的数据与分类输出、至少 3 分钟质量报告、Web/手机网页、部署说明和实际性能报告。
条件交付：三分类全量在线吞吐、INT8 板端运行、LF/HF 板端计算，必须按板测结果标明是否完成。
扩展交付：真正可安装的移动 App、协议自动恢复、可选 3D 外壳。
明确不覆盖：现有模型没有的房颤识别、其他生理信号实测、临床可靠诊断；界面不显示未接传感器的虚构参数。
保留版本/测试/修改记录，供课程 AI 辅助开发日志和报告追溯。
